# Testing in literate (noweb) projects

In a literate project the `.nw` files are the source. Tests are chunks in
them, and `tests/test_*.py` is generated by tangling, often gitignored and
deleted by `make clean`. Every rule in SKILL.md still applies; this file
says where each one lands. Load the `literate-programming` skill for the
editing itself.

## Where things live

| Item | Normal project | Literate project |
|---|---|---|
| a test | `tests/test_mod.py` | a `<<test functions>>` (or similar) chunk in `src/.../mod.nw`, tangled to `tests/test_mod.py` |
| why a test steps down the ladder | a comment or docstring | the prose before the test chunk |
| fixtures shared by many tests | `tests/conftest.py` | a committed `tests/conftest.py`, or a chunk tangled to it (see below) |
| recorded cassettes | `tests/cassettes/` | the same, committed; they are data, never tangled |
| what to scan before committing | `tests/` | the `.nw` sources, plus the woven outputs before publishing |

Find the project's convention first: read its `CLAUDE.md`, the tests
`Makefile` (the rule that runs `notangle`) and `.gitignore`.

## Writing a test

Red/green works as usual, with tangling in the loop:

1. Write the test chunk in the `.nw`, placed after the code it verifies,
   with prose saying what behaviour it pins down and why.
2. Run the project's test target (`make test`, or `make -C tests`), which
   tangles and runs pytest. Confirm the new test fails for the right
   reason.
3. Change the code chunk, run the target again, and see it pass.

Never edit the tangled `tests/test_*.py`: the next tangle overwrites it,
and the change never reaches the repository. And judge tests from the
`.nw`, not the tangled file: a test chunk may include production chunks,
so what looks like a copy of the logic can be the real code.

## The templates

`assets/conftest.py` and `assets/vcr_support.py` are ordinary Python.
Two ways to bring them in:

- **Commit them as plain files** in `tests/`, if the project allows
  non-generated Python there. Check that `.gitignore` (`test_*.py`,
  `*.py`) and `make clean` leave them alone.
- **Tangle them from a `.nw`**, if the project's rule is that all code
  comes from `.nw` files. Put them in a chapter about the test setup
  (`tests/conftest.nw`, or a section of the main document), as chunks
  `<<conftest.py>>=` and `<<vcr_support.py>>=`, and add the files to the
  tangling rules. Adapt the key lists in prose: each LADOK or Canvas key
  added deserves a sentence on what it holds.

## Cassettes and `make clean`

Cassettes are recorded data, not generated code. They must survive
`make clean` and must not be gitignored:

- `tests/cassettes/<module>/<test>.yaml` is keyed by the tangled module
  name (`test_api`), so keep the tangled file names stable;
- check that `clean` targets remove only the tangled files, never
  `tests/*` or `tests/cassettes`;
- `git clean -X` and similar remove ignored files only; cassettes are
  committed, so they are safe from it.

## Running, mutating and scanning

- **First run**: `~/.claude/skills/testing/scripts/offline_run.py -- make test`.
  The environment reaches the tangle step and pytest alike. Tangling
  needs no network.
- **Mutations**: mutate the `.nw` and give the command that tangles and
  tests, so the check runs on what will be committed:
  `mutate.py src/pkg/mod.nw "logger.info(" "logger.debug(" -- make test`.
  A fix found this way also goes into the `.nw`. `mutate.py` restores
  the `.nw`, but the tangled files keep the mutant until the next build:
  run `make` before trying anything by hand.
- **Scanning**: with no paths, `scan_leaks.py` scans `tests/` and every
  `.nw` file git tracks. As a pre-commit hook, let it run on the
  committed `.nw` files:

  ```yaml
  - repo: local
    hooks:
      - id: scan-test-data
        name: scan sources and test data for personal data and secrets
        entry: python3 ~/.claude/skills/testing/scripts/scan_leaks.py
        language: system
        files: (\.nw$|^tests/)
  ```

## Documentation that runs live code

Literate documents often run code at weave time (PythonTeX `pycode`,
`\py{}`), and the output is typeset into a PDF that may be published,
for example attached to a release. That output is test output in the
sense of layer 4 (SKILL.md section 4), and it reaches more readers:

- print only the keys the text needs (`{k: r[k] for k in ("Kurskod",
  "Omfattning")}`), not a whole record passed through a scrubber that
  lists the keys to *remove*. An allowlist fails safe when the service
  adds a field; a denylist leaks it;
- if whole records must be shown, scrub them with the same
  `Pseudonymizer` the cassettes use, so free text (LADOK's `Anteckning`)
  is redacted too;
- recorded responses pasted into the prose as examples are published
  data: replace them with synthetic records, as for cassettes;
- before publishing, run `scan_leaks.py --key-census` on the generated
  output to see which keys carry free text, then scan it, for example
  `scan_leaks.py pythontex-files-*/ doc/*.stdout`, and the PDF itself
  with `pdftotext doc.pdf - | scan_leaks.py -`;
- never print a whole configuration or environment (`tool config`,
  `env`, a settings dump): the author's config holds private links (a
  calendar's secret address, a schedule URL with a token), paths and
  colleagues' names. Show a synthetic example config in a `minted`
  block, or print an allowlist of keys;
- add the PDF scan to the publish target, so that no release goes out
  unscanned: `pdftotext doc/x.pdf - | scan_leaks.py --originals
  /dev/null -` before `gh release create`;
- a weave that calls the service live depends on credentials and on the
  data of the day. Where possible, weave from recorded data instead.
  Where a live example is kept on purpose, it is a smoke test of the
  real service: make the build fail when the command fails, and assert
  something about the output (a known course code appears), not only
  that it ran.
